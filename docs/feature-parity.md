# 功能对齐规格（clean-room）

本文档是**观察阶段的产物**：只用普通用户视角能看到的抖音产品行为作为规格来源。
文中不含任何反编译产物、字节跳动素材、字体、图标、接口签名算法或私有协议字段。
实现一律从本规格出发，由自有代码独立完成。

---

## 1. 现状基线（可核验）

| 层 | 证据 | 当前能力 |
|---|---|---|
| 服务端 | `server/src/api.js` 32 条 `route()` | 鉴权、用户、关注、推荐流/关注流、发布、点赞、收藏、播放、分享、评论（一级回复）、搜索、私信 |
| 数据模型 | `server/src/db.js:7-129` | `users / media_objects / videos / likes / favorites / follows / comments / comment_likes / threads / messages / thread_reads` |
| 网页端 | `web/src/pages/` 7 个页面 | Feed、视频详情、搜索、上传、消息、个人主页、登录 |
| 桌面端 | `desktop/src/backend.cjs` | Electron 壳 + 内嵌后端自举，**无独有能力** |
| 安卓端 | `android/app/src/main/java/` | WebView 壳 + 全屏/桥接/服务器配置，**无独有能力** |

一句话结论：**三端功能完全等价于网页端，安卓端相比抖音缺的不是"壳"，而是整个内容生产与分发的产品层。**

## 2. 可观察行为规格

按"用户能直接看到什么"描述，不描述对方内部实现。

### 2.1 信息流与播放

| 编号 | 可观察行为 | 现状 | 差距 |
|---|---|---|---|
| FEED-1 | 顶部多个 Tab：推荐 / 关注 / 同城 / 探索，切换后流内容不同 | 仅推荐+关注 | 缺同城、探索 |
| FEED-2 | **图集**：一条内容是 N 张图片，左右滑动，配一段音乐，会按节奏自动轮播，末图停留 | ❌ 完全缺失 | 大 |

| FEED-7 | 弹幕开关，弹幕随进度滚动 | ❌ | 中 |
| FEED-8 | 看完的进度会被记住，下次进来从中断处继续（跨端一致） | ❌ | 中，但**正是三端产品的卖点** |

| 编号 | 可观察行为 | 现状 | 差距 |
|---|---|---|---|
| MSG-1 | 私信发图片/视频/语音 | 纯文本 | 中 |

### 2.7 多端同步语义

这一节对**三端产品**最重要，因为差异体现在端与端之间。

| 编号 | 规格（观察 + 设计判断） | 现状 |
|---|---|---|
| SYNC-1 | 登录态：同一账号可在网页/桌面/手机并存，可远程登出某一端 | ❌ 无设备维度 |
| SYNC-2 | 收藏、喜欢、关注、关注流：**全端一致**（服务端派生，天然一致） | ✅ |
| SYNC-3 | 观看进度：**跨端续播**（服务器记录，任一端接着看） | ❌ |
| SYNC-4 | **草稿：仅存本机，不跨端同步** —— 抖音的实际观察行为，且是刻意的（避免半成品上云）。我们的三端应照抄这个语义 | ❌ |
| SYNC-5 | 通知未读数与消息已读：全端一致 | ❌（已读在服务端，但未聚合） |

> ⚠️ SYNC-4 是这条规格里唯一需要**真机核验**的承重结论：它决定草稿箱做成本地存储还是服务端表。核验方式很简单 —— 手机发一条草稿，网页端登录同账号看是否出现。核验前，实现按"本地优先 + 可选上云开关"设计，两种结论都不返工。

### 2.8 明确不做

直播、电商/橱窗/团购、本地生活、支付、提现、内容审核后台、美颜特效引擎。
理由：需要真实基建、牌照资质或 GPU 管线，且**任何一条都不是逆向能带过来的** —— 它们在服务端和资质里。本项目不假装拥有这些能力。

## 3. 差距归类与分期建议

按"实现它需要什么"分类，而不是按看起来像不像抖音分类：

- **A 类｜纯自有实现，零基建依赖** —— 改 DB + API + 三端 UI 就能做完整。
- **B 类｜需要自建服务端能力** —— 要加管线/协议（WebSocket、FTS5、定时任务）。
- **C 类｜需要媒体基建** —— 转码、切片、雪碧图、对象存储、CDN。
- **D 类｜不做** —— 见 §2.8。

| 期 | 内容 | 类 | 为什么这个顺序 |
|---|---|---|---|
| **P0** | 草稿箱（含 SYNC-4 语义）、图集 FEED-2/PUB-6、发布可见性 PUB-2、话题实体 SRC-4、多级评论 INT-1 + `@` INT-3、通知中心 SOC-1、负反馈 FEED-3、屏蔽/举报 INT-6 | A | 这批就是"安卓端独有、桌面网页端没有"的产品层本体，且全部零基建依赖 |
| **P1** | 搜索联想 SRC-1 + 历史 SRC-2 + FTS5 SRC-5、跨端续播 SYNC-3 + 观看历史、转发带评论 INT-4、合集/稍后再看 INT-5、定时发布 PUB-5、封面选帧 PUB-4 | A/B | 补齐留存与发现闭环，仍不碰基建 |
| **P2** | WebSocket 实时私信 MSG-1/2/3、设备级登录态 SYNC-1、弹幕 FEED-7、自动连播 FEED-6 | B | 需要协议改动，收益明确但成本高一档 |
| **P3** | 多码率+清晰度 FEED-5、进度条缩略图 FEED-4、同城 FEED-1 | C | 必须先有 ffmpeg 转码管线，否则做出来是假的 |

## 4. 边界声明

- 本规格的来源是公开产品行为与交互模式，与 README 第 14 行的免责声明一致。
- 不引入：抖音/字节代码、商标、图标、字体、视频内容、`a_bogus` / `X-Bogus` / `msToken` 一类签名算法。
- 服务端一律用自有协议；客户端一律自有实现。功能"对齐"指**用户可见行为等价**，不指实现相同。
